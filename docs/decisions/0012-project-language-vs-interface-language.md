# ADR 0012: Separate the project language from the interface language

**Status:** Accepted

The platform speaks French, English and Arabic through two independent settings. The **project language** is chosen when a project is created and stored on the project. Every AI generation for that project and every exported deliverable (Word, PDF, Excel) uses it: profile chat, internal-context assistance, external research, issue synthesis, regulatory discovery, applicability and conformity. The **interface language** is a per-user preference stored in `User.locale`. It drives the screens, dates and numbers, and nothing else. A French-speaking consultant can therefore run an Arabic project and hand its client an Arabic register without the application ever switching to Arabic.

The project language cannot be changed after creation. Cross-run identity (the canonical keys and fingerprints of context issues and factors) is derived from the generated wording, and a register mixing two languages would not be a coherent deliverable. A project that needs another language is recreated. Because the language is fixed, regulatory runs read it from the profile snapshot. Snapshots taken before this decision carry no language and are treated as French, which is what every earlier project was.

Enum values and keys the AI must emit stay the existing French identifiers whatever the output language: issue nature `force | faiblesse | opportunite | menace`, factor orientation and evidence strength, and PESTEL dimension names. Prompts state this explicitly, the code keeps matching on stable keys (`pestelDimensionKey` also recognises English and Arabic wording), and only the display is translated. Quoted regulatory text (`requirementText`, supporting excerpts) always stays in the language of its source document. Corpus-side languages (`Document.language`, the `languages` filter of an analysis run, knowledge-example retrieval) describe source material and are unrelated to either setting.

The interface is translated with typed i18next catalogs in `apps/client-web/src/locales`. French is the source, and a catalog must have exactly its keys (Arabic may add its extra CLDR plural forms). Arabic switches the document to right-to-left, and components use logical CSS (`ms-*`, `start-*`, `text-start`, `inline-end` sides). PDF export is not offered for Arabic projects yet, because jsPDF's built-in fonts have no Arabic glyphs; Word and Excel exports support Arabic natively.
